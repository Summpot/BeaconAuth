## Chemins de base

L’API est servie sur:

- `/v1/*` (direct)
- `/api/v1/*` (lorsqu’elle est montée sous `/api`)

## Endpoints principaux

### Sessions

- `POST /v1/login`
- `POST /v1/register`
- `POST /v1/refresh`
- `POST /v1/logout`
- `GET /v1/user/me`
- `GET /v1/user/me/avatar`
- `POST /v1/user/change-password`
- `POST /v1/user/change-username`
- `POST /v1/user/profile`

Exemple: `POST /v1/login`

```json
{
  "username": "player123",
  "password": "secure_password"
}
```

### Authentification Minecraft (OIDC)

Le mod Minecraft utilise un flux OIDC standard code d'autorisation + PKCE :

- `GET /.well-known/openid-configuration` — découverte OIDC
- `GET /v1/oidc/authorize` — endpoint d'autorisation (le mod l'ouvre via l'UI de connexion)
- `POST /v1/oidc/complete` — la SPA termine l'autorisation et redirige vers le mod
- `POST /v1/oidc/token` — endpoint de token (sans client secret, lié au PKCE)
- `GET /v1/oidc/userinfo` — endpoint userinfo (autorisé par access token)

### Identité Minecraft

Lorsqu'un joueur premium vérifié Mojang est servi via le chemin de contournement online-mode, le
mod peut résoudre si un UUID Mojang est lié à un compte BeaconAuth et comment gérer son identité :

- `GET /v1/minecraft/lookup?uuid=<mojangUuid>` — authentifié avec le secret partagé
  `X-Minecraft-Auth` (`MINECRAFT_LOOKUP_SECRET`). Renvoie `{ bound, identity_mode, user_subject,
  textures_value, textures_signature }`.
- `GET /v1/minecraft/identity-mode` — la préférence d'identité effective de l'utilisateur actuel.
- `POST /v1/minecraft/identity-mode` — définit la préférence de l'utilisateur actuel
  (`mojang`/`legacy`).

### OAuth

- `POST /v1/oauth/start`
- `POST /v1/oauth/link/start`
- `GET /v1/oauth/callback`

Fournisseurs pris en charge : `github`, `google`, `microsoft` (Entra ID) et `minecraft` (Microsoft
consumer + Xbox, réutilisant les identifiants `MICROSOFT_CLIENT_ID`/`MICROSOFT_CLIENT_SECRET`). Le
fournisseur `minecraft` lie le véritable UUID Mojang comme identité du fournisseur.

### Passkeys (WebAuthn)

- `POST /v1/passkey/register/start`
- `POST /v1/passkey/register/finish`
- `POST /v1/passkey/auth/start`
- `POST /v1/passkey/auth/finish`
- `POST /v1/passkey/delete`
- `GET /v1/passkey/list`
- `DELETE /v1/passkey/{id}`

### Identités

- `GET /v1/identities`
- `DELETE /v1/identities/{id}`

### Configuration et JWKS

- `GET /v1/config`
- `GET /.well-known/jwks.json`

### Admin

- `POST /v1/admin/migrations/up`

## Notes

- Les endpoints de session posent des cookies HttpOnly pour les tokens access/refresh.
- Les JWT sont signés en ES256 et publiés via JWKS.
- Certains endpoints nécessitent une session authentifiée.
