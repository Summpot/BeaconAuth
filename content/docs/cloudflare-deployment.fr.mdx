## Vue d’ensemble

BeaconAuth prend en charge un déploiement séparé:

- **Cloudflare Pages** pour l’UI React.
- **Cloudflare Worker** (`crates/beacon-worker`) pour l’API.

Les deux déploiements partagent le même nom de projet (`name`) dans `wrangler.jsonc` et
`wrangler.workers.jsonc` (le CI le vérifie).

## Configs Wrangler

- `wrangler.jsonc`: config Cloudflare Pages (sortie UI dans `dist/`).
- `wrangler.workers.jsonc`: config Cloudflare Worker (sortie wasm).

## Workflows CI

- `.github/workflows/deploy-cloudflare-pages.yml` déploie l’UI.
- `.github/workflows/deploy-cloudflare-worker.yml` déploie le worker API et applique les migrations.

### Secrets requis (Pages)

- `CLOUDFLARE_API_TOKEN`
- `CLOUDFLARE_ACCOUNT_ID`

Optionnel:

- `SENTRY_AUTH_TOKEN`

### Secrets requis (Worker)

- `CLOUDFLARE_API_TOKEN`
- `CLOUDFLARE_ACCOUNT_ID`
- `TURSO_PLATFORM_API_TOKEN`
- `TURSO_ORG_SLUG`
- `TURSO_DB_NAME`

Optionnel:

- `TURSO_GROUP` (par défaut `default`)
- `CLOUDFLARE_WORKER_BASE_URL` (par défaut `https://<name>.pages.dev`)
- `CLOUDFLARE_WORKER_LIBSQL_URL` (override libSQL au lieu de l’API Turso)
- `CLOUDFLARE_WORKER_LIBSQL_AUTH_TOKEN`
- `CLOUDFLARE_MIGRATIONS_API_TOKEN` (utilisé pour `/v1/admin/migrations/up`)
- Secrets des fournisseurs OAuth (voir ci-dessous)

### Secrets Worker optionnels pour OAuth

- `CLOUDFLARE_WORKER_GITHUB_CLIENT_ID`
- `CLOUDFLARE_WORKER_GITHUB_CLIENT_SECRET`
- `CLOUDFLARE_WORKER_GOOGLE_CLIENT_ID`
- `CLOUDFLARE_WORKER_GOOGLE_CLIENT_SECRET`
- `CLOUDFLARE_WORKER_MICROSOFT_CLIENT_ID`
- `CLOUDFLARE_WORKER_MICROSOFT_CLIENT_SECRET`
- `CLOUDFLARE_WORKER_MICROSOFT_TENANT`

## Routage single-origin (optionnel)

Si vous voulez que l’UI et l’API partagent une seule origine, le dépôt le supporte déjà via
l’entrée serveur Nitro.

- L’entrée serveur se trouve dans `src/server.ts`.
- Nitro génère automatiquement le bundle worker Cloudflare Pages (`_worker.js`) pendant le build.
	Aucun fichier d’entrée worker Pages manuel n’est nécessaire.
- Assurez-vous que le projet Pages a un service binding nommé `BACKEND` pointant vers le worker API
	(voir `wrangler.jsonc`).

Par défaut, l’entrée serveur proxy les requêtes dont le chemin commence par `/api/`, `/v1/`, ou
`/.well-known/` vers `env.BACKEND` et sert l’UI pour le reste.

## Notes

- Le déploiement Worker utilise libSQL/Turso (définir `LIBSQL_URL` et `LIBSQL_AUTH_TOKEN`).
- Les migrations sont appliquées via l’endpoint Worker `POST /v1/admin/migrations/up` dans le CI.
