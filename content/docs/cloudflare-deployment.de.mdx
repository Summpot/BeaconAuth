## Überblick

BeaconAuth unterstützt ein geteiltes Deployment:

- **Cloudflare Pages** für die React-UI.
- **Cloudflare Worker** (`crates/beacon-worker`) für die API.

Beide Deployments teilen sich denselben Projektnamen (`name`) in `wrangler.jsonc` und
`wrangler.workers.jsonc` (CI erzwingt das).

## Wrangler-Konfigurationen

- `wrangler.jsonc`: Cloudflare Pages Config (UI Build-Output in `dist/`).
- `wrangler.workers.jsonc`: Cloudflare Worker Config (wasm Build-Output).

## CI-Workflows

- `.github/workflows/deploy-cloudflare-pages.yml` deployt die UI.
- `.github/workflows/deploy-cloudflare-worker.yml` deployt den API-Worker und führt Migrationen aus.

### Erforderliche Secrets (Pages)

- `CLOUDFLARE_API_TOKEN`
- `CLOUDFLARE_ACCOUNT_ID`

Optional:

- `SENTRY_AUTH_TOKEN`

### Erforderliche Secrets (Worker)

- `CLOUDFLARE_API_TOKEN`
- `CLOUDFLARE_ACCOUNT_ID`
- `TURSO_PLATFORM_API_TOKEN`
- `TURSO_ORG_SLUG`
- `TURSO_DB_NAME`

Optional:

- `TURSO_GROUP` (Standard: `default`)
- `CLOUDFLARE_WORKER_BASE_URL` (Standard: `https://<name>.pages.dev`)
- `CLOUDFLARE_WORKER_LIBSQL_URL` (libSQL-URL statt Turso API überschreiben)
- `CLOUDFLARE_WORKER_LIBSQL_AUTH_TOKEN`
- `CLOUDFLARE_MIGRATIONS_API_TOKEN` (für `/v1/admin/migrations/up`)
- OAuth-Provider-Secrets (siehe unten)

### Optionale Worker-Secrets für OAuth

- `CLOUDFLARE_WORKER_GITHUB_CLIENT_ID`
- `CLOUDFLARE_WORKER_GITHUB_CLIENT_SECRET`
- `CLOUDFLARE_WORKER_GOOGLE_CLIENT_ID`
- `CLOUDFLARE_WORKER_GOOGLE_CLIENT_SECRET`
- `CLOUDFLARE_WORKER_MICROSOFT_CLIENT_ID`
- `CLOUDFLARE_WORKER_MICROSOFT_CLIENT_SECRET`
- `CLOUDFLARE_WORKER_MICROSOFT_TENANT`

## Single-Origin-Routing (optional)

Wenn UI und API eine gemeinsame Origin teilen sollen, wird das bereits über den Nitro-Server-Entry
unterstützt.

- Der Server-Entry befindet sich in `src/server.ts`.
- Nitro erzeugt während des Builds automatisch das Cloudflare Pages Worker-Bundle (`_worker.js`).
	Keine manuelle Pages-Worker-Entry-Datei nötig.
- Stelle sicher, dass das Pages-Projekt ein Service Binding namens `BACKEND` hat, das auf deinen
	API-Worker zeigt (siehe `wrangler.jsonc`).

Standardmäßig proxyt der Server-Entry Requests, deren Pfad mit `/api/`, `/v1/` oder `/.well-known/`
beginnt, an `env.BACKEND` und liefert die UI für alles andere aus.

## Hinweise

- Das Worker-Deployment nutzt libSQL/Turso (setze `LIBSQL_URL` und `LIBSQL_AUTH_TOKEN`).
- Migrationen werden in CI über den Worker-Endpoint `POST /v1/admin/migrations/up` angewendet.
