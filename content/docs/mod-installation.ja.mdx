## サーバーへの導入

1. BeaconAuth を見つけた配布プラットフォームのファイルページから、対応する MOD jar をダウンロードします。
   - CurseForge: Files タブで Minecraft バージョンとローダーに合う jar を選択します。
   - Modrinth: Versions タブで Minecraft バージョンとローダーに合う jar を選択します。
   - Fabric: `beaconauth-fabric-*.jar`
   - Forge: `beaconauth-forge-*.jar`
   - NeoForge: `beaconauth-neoforge-*.jar`
2. jar をサーバーの `mods/` ディレクトリに配置します。
3. サーバーを再起動します。

## クライアントへの導入

1. サーバーと同じ MOD jar を同じ配布プラットフォームからダウンロードします。
2. クライアントの `mods/` ディレクトリに配置します。
3. ゲームを起動し、求められたら認証します。

## 対応バージョン

このリポジトリは Minecraft 1.19.2 / 1.20.1 / 1.21.1 / 1.21.8 向けのローダーを同梱しています（`modSrc/` を参照）。

## MOD の設定

サーバーを初回起動すると、以下に設定ファイルが生成されます:

- `config/beaconauth-server.toml`

例:

```toml
[authentication]
# Base URL of your authentication server
# Example: https://beaconauth.pages.dev (development) or https://auth.example.com (production)
# WARNING: Always use HTTPS in production!
base_url = "https://beaconauth.pages.dev"

# JWKS (JSON Web Key Set) URL for JWT signature verification (fallback)
# Usually: <base_url>/.well-known/jwks.json
# Empty means: derive from base_url
jwks_url = ""

[jwt]
# Expected JWT audience (aud claim)
audience = "minecraft-client"

[jku]
# JWT JWKS Discovery (JKU)
# If allowed_host_patterns is non-empty and the JWT has a 'jku' header, BeaconAuth will fetch keys from that JWKS URL.
# Security: You MUST restrict allowed hosts to avoid SSRF.
# When enabled, JKU ALWAYS requires https://.
# Empty means: JKU disabled (BeaconAuth will ignore token 'jku' and only use authentication.jwks_url).
allowed_host_patterns = "beaconauth.pages.dev, *.beaconauth.pages.dev"

[behavior]
# If true: Players with verified Mojang sessions may continue without the BeaconAuth web flow when server is in online-mode
bypass_if_online_mode_verified = true
# If true: Modded clients MUST authenticate when server is offline-mode
force_auth_if_offline_mode = true
# Only applies when force_auth_if_offline_mode is true
# If true: offline-mode vanilla clients (without BeaconAuth mod) are allowed in.
allow_vanilla_offline_clients = true
# レガシー オフライン ID モード（既存の offline-mode サーバー移行用）：
# - true の場合：各 BeaconAuth アカウントは、初回の認証ログイン時に主張したオフライン UUID
#   （"OfflinePlayer:<名前>"）に紐付けられ、以後その ID が固定されます。
# - ワールドデータ（playerdata/、stats/、advancements/）はファイル名変更なしで保持されます。
# - マッピングはワールドごとに <ワールドディレクトリ>/beaconauth-identities.json に保存されます。
# - セキュリティ：ID は初回ログイン時のユーザー名に紐付くため、後から同名で登録した
#   アカウントも同じ UUID にマッピングされます。小規模サーバー向けです。
use_legacy_offline_uuids = false
```

### メモ

- `authentication.base_url` はログイン URL の生成と JWT の想定 issuer（`iss`）に使われます。
- `authentication.jwks_url` は空の場合、既定で `${base_url}/.well-known/jwks.json` が使われます。
- `jku.allowed_host_patterns` はカンマ/スペース区切りの allowlist です。対応パターン:
  - `example.com`, `*.example.com`
  - 非対応: 単独の `*` や `auth*.example.com` のような文字列途中のワイルドカード

### 既存の offline-mode サーバーの移行（レガシー ID）

1. `behavior.use_legacy_offline_uuids = true` を有効にし、サーバーは offline-mode のままにします。
2. 各プレイヤーの初回 BeaconAuth ログイン時に、mod はアカウントをオフライン UUID
   （`OfflinePlayer:<名前>`）に紐付け、`<ワールドディレクトリ>/beaconauth-identities.json` に保存します。
   既存の `playerdata/`、`stats/`、`advancements/` はファイル名変更なしでそのまま使えます。
3. 移行を計画するには、`/beaconauth unmigrated`（権限レベル 2）を実行します。まだどの
   BeaconAuth アカウントにも認領されていない `playerdata/` 内の各オフラインプロファイルを、
   名前が分かる場合はその名前とともに一覧表示します。サーバーは起動時にも総数をログに記録します。
4. レガシー ID は一度しか認領できません：別の BeaconAuth アカウントが同じ名前でログインしようとすると、
   黙って ID を引き継ぐのではなく、明確なメッセージとともにログインが拒否されます。
5. 誤操作の救済：サーバーオペレーター（権限レベル 2）は
   `/beaconauth transfer-identity <Minecraft名> <BeaconAuthユーザー名>` で ID を移行できます。
6. 移行完了後もマッピングは有効です。あとでこのモードを無効にすると、アカウントは安定した
   per-account UUID（新しいワールドデータ、旧データとは関連しません）に戻ります。
