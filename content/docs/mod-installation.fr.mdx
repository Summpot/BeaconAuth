## Installation serveur

1. Téléchargez le jar correspondant depuis la page des fichiers de la plateforme où vous avez trouvé BeaconAuth.
   - CurseForge : utilisez l’onglet Files et choisissez le jar adapté à votre version de Minecraft et à votre loader.
   - Modrinth : utilisez l’onglet Versions et choisissez le jar adapté à votre version de Minecraft et à votre loader.
   - Fabric: `beaconauth-fabric-*.jar`
   - Forge: `beaconauth-forge-*.jar`
   - NeoForge: `beaconauth-neoforge-*.jar`
2. Placez le jar dans le dossier `mods/` du serveur.
3. Redémarrez le serveur.

## Installation client

1. Téléchargez le même jar que celui du serveur depuis la même plateforme de publication.
2. Placez-le dans le dossier `mods/` du client.
3. Lancez le jeu et authentifiez-vous lorsque demandé.

## Versions supportées

Le dépôt fournit des loaders pour Minecraft 1.19.2, 1.20.1, 1.21.1 et 1.21.8 (voir `modSrc/`).

## Configuration du mod

Après le premier démarrage du serveur, un fichier de configuration est généré:

- `config/beaconauth-server.toml`

Exemple:

```toml
[authentication]
# Base URL of your authentication server
# Example: https://beaconauth.pages.dev (development) or https://auth.example.com (production)
# WARNING: Always use HTTPS in production!
base_url = "https://beaconauth.pages.dev"

# JWKS (JSON Web Key Set) URL for JWT signature verification (fallback)
# Usually: <base_url>/.well-known/jwks.json
# Empty means: derive from base_url
jwks_url = ""

[jwt]
# Expected JWT audience (aud claim)
audience = "minecraft-client"

[jku]
# JWT JWKS Discovery (JKU)
# If allowed_host_patterns is non-empty and the JWT has a 'jku' header, BeaconAuth will fetch keys from that JWKS URL.
# Security: You MUST restrict allowed hosts to avoid SSRF.
# When enabled, JKU ALWAYS requires https://.
# Empty means: JKU disabled (BeaconAuth will ignore token 'jku' and only use authentication.jwks_url).
allowed_host_patterns = "beaconauth.pages.dev, *.beaconauth.pages.dev"

[behavior]
# If true: Players with verified Mojang sessions may continue without the BeaconAuth web flow when server is in online-mode
bypass_if_online_mode_verified = true
# If true: Modded clients MUST authenticate when server is offline-mode
force_auth_if_offline_mode = true
# Only applies when force_auth_if_offline_mode is true
allow_vanilla_offline_clients = false
# Mode d'identité hors ligne hérité (pour migrer un serveur offline-mode existant) :
# - Si true : chaque compte BeaconAuth est mappé à l'UUID hors ligne ("OfflinePlayer:<nom>")
#   qu'il a revendiqué lors de sa première connexion authentifiée, et conserve cette identité.
# - Les données du monde (playerdata/, stats/, advancements/) sont préservées sans renommer de fichiers.
# - Le mappage est stocké par monde dans <répertoire du monde>/beaconauth-identities.json.
# - Sécurité : l'identité est liée au nom utilisé à la première connexion ; un autre compte
#   s'inscrivant plus tard avec le même nom obtiendrait la même UUID. Conçu pour les petits serveurs.
use_legacy_offline_uuids = false
```

### Notes

- `authentication.base_url` est utilisé pour construire les URLs de login et l’issuer JWT attendu (`iss`).
- `authentication.jwks_url` vaut par défaut `${base_url}/.well-known/jwks.json` quand vide.
- `jku.allowed_host_patterns` est une allowlist séparée par virgules/espaces. Motifs supportés:
  - `example.com`, `*.example.com`
  - Non supporté: `*` seul ou jokers au milieu comme `auth*.example.com`

### Migration d'un serveur offline-mode existant (identités héritées)

1. Activez `behavior.use_legacy_offline_uuids = true` et conservez le serveur en offline-mode.
2. Lors de la première connexion BeaconAuth d'un joueur, le mod lie le compte à l'UUID hors ligne
   (`OfflinePlayer:<nom>`) et écrit `<répertoire du monde>/beaconauth-identities.json`, si bien que
   les `playerdata/`, `stats/` et `advancements/` existants continuent de fonctionner sans renommage.
3. Pour planifier la migration, exécutez `/beaconauth unmigrated` (niveau de permission 2). La
   commande liste chaque profil hors ligne de `playerdata/` qui n'a encore été revendiqué par aucun
   compte BeaconAuth, avec le nom du joueur quand il est disponible ; le serveur journalise aussi le
   nombre total au démarrage.
4. Une identité héritée ne peut être revendiquée qu'une seule fois : si un autre compte BeaconAuth
   tente ensuite de se connecter avec le même nom, la connexion est refusée avec un message clair,
   au lieu d'être silencieusement associée.
5. Correction en cas d'erreur : un opérateur du serveur (niveau de permission 2) peut transférer
   une identité avec `/beaconauth transfer-identity <nomMinecraft> <nomUtilisateurBeaconAuth>`.
6. Une fois la migration terminée, l'association reste active ; désactiver ensuite le mode fait
   revenir les comptes à des UUID stables par compte (nouvelles données du monde, pas les anciennes).
