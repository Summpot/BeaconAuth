## 概览

BeaconAuth 支持拆分部署：

- **Cloudflare Pages**：用于 React UI。
- **Cloudflare Worker**（`crates/beacon-worker`）：用于 API。

两个部署在 `wrangler.jsonc` 与 `wrangler.workers.jsonc` 中必须使用相同的 `name`（CI 会强制校验）。

## Wrangler 配置

- `wrangler.jsonc`：Cloudflare Pages 配置（UI 输出到 `dist/`）。
- `wrangler.workers.jsonc`：Cloudflare Worker 配置（wasm 输出）。

## CI 工作流

- `.github/workflows/deploy-cloudflare-pages.yml` 部署 UI。
- `.github/workflows/deploy-cloudflare-worker.yml` 部署 API Worker 并应用迁移。

### Pages 必需 secrets

- `CLOUDFLARE_API_TOKEN`
- `CLOUDFLARE_ACCOUNT_ID`

可选：

- `SENTRY_AUTH_TOKEN`

### Worker 必需 secrets

- `CLOUDFLARE_API_TOKEN`
- `CLOUDFLARE_ACCOUNT_ID`
- `TURSO_PLATFORM_API_TOKEN`
- `TURSO_ORG_SLUG`
- `TURSO_DB_NAME`

可选：

- `TURSO_GROUP`（默认 `default`）
- `CLOUDFLARE_WORKER_BASE_URL`（默认 `https://<name>.pages.dev`）
- `CLOUDFLARE_WORKER_LIBSQL_URL`（覆盖 Turso API 生成的 libSQL URL）
- `CLOUDFLARE_WORKER_LIBSQL_AUTH_TOKEN`
- `CLOUDFLARE_MIGRATIONS_API_TOKEN`（用于 `/v1/admin/migrations/up`）
- OAuth 提供商 secrets（见下文）

### Worker 的 OAuth 可选 secrets

- `CLOUDFLARE_WORKER_GITHUB_CLIENT_ID`
- `CLOUDFLARE_WORKER_GITHUB_CLIENT_SECRET`
- `CLOUDFLARE_WORKER_GOOGLE_CLIENT_ID`
- `CLOUDFLARE_WORKER_GOOGLE_CLIENT_SECRET`
- `CLOUDFLARE_WORKER_MICROSOFT_CLIENT_ID`
- `CLOUDFLARE_WORKER_MICROSOFT_CLIENT_SECRET`
- `CLOUDFLARE_WORKER_MICROSOFT_TENANT`

## 单域路由（可选）

如果希望 UI 与 API 共享同一域名，本仓库已通过 Nitro 的 server entry 支持该模式。

- server entry 位于 `src/server.ts`。
- Nitro 会在构建时自动生成 Cloudflare Pages 的 worker bundle（`_worker.js`），无需手动维护 Pages worker 入口文件。
- 确保 Pages 项目存在名为 `BACKEND` 的服务绑定并指向 API Worker（见 `wrangler.jsonc`）。

默认情况下，server entry 会将路径以 `/api/`、`/v1/` 或 `/.well-known/` 开头的请求代理到 `env.BACKEND`，其余请求用于提供 UI。

## 备注

- Worker 部署使用 libSQL/Turso（设置 `LIBSQL_URL` 与 `LIBSQL_AUTH_TOKEN`）。
- 迁移会在 CI 中通过 Worker 端点 `POST /v1/admin/migrations/up` 应用。
