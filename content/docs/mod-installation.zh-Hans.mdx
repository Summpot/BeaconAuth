description: 安装并配置 BeaconAuth Minecraft 模组。
---

## 服务端安装

1. 从你找到 BeaconAuth 的发布平台文件页下载匹配的模组 jar。
   - CurseForge：在 Files 页选择与你的 Minecraft 版本和加载器匹配的 jar。
   - Modrinth：在 Versions 页选择与你的 Minecraft 版本和加载器匹配的 jar。
   - Fabric：`beaconauth-fabric-*.jar`
   - Forge：`beaconauth-forge-*.jar`
   - NeoForge：`beaconauth-neoforge-*.jar`
2. 将 jar 放入服务器 `mods/` 目录。
3. 重启服务器。

## 客户端安装

1. 从同一发布平台下载与服务端相同版本的模组 jar。
2. 将 jar 放入客户端 `mods/` 目录。
3. 启动游戏并按提示认证。

## 支持版本

仓库提供 Minecraft 1.19.2、1.20.1、1.21.1 与 1.21.8 的加载器（详见 `modSrc/`）。

## 模组配置

首次启动服务器后会生成配置文件：

- `config/beaconauth-server.toml`

示例配置：

```toml
[authentication]
# 认证服务器的 Base URL
# 示例：https://beaconauth.pages.dev（开发）或 https://auth.example.com（生产）
# 警告：生产环境务必使用 HTTPS！
base_url = "https://beaconauth.pages.dev"

# JWT 签名验证用的 JWKS URL（兜底）
# 通常为：<base_url>/.well-known/jwks.json
# 留空：由 base_url 推导
jwks_url = ""

[jwt]
# 期望的 JWT audience（aud）
audience = "minecraft-client"

[jku]
# JWT 的 JWKS Discovery（JKU）
# 当 allowed_host_patterns 非空且 JWT 头含 jku 时，会从该 JWKS URL 拉取密钥。
# 安全提示：必须限制允许的主机以避免 SSRF。
# 启用时，JKU 必须使用 https://
# 留空表示禁用 JKU（忽略 token 的 jku，仅使用 authentication.jwks_url）
allowed_host_patterns = "beaconauth.pages.dev, *.beaconauth.pages.dev"

[behavior]
# online-mode（推荐 true）：
# - 正版玩家可不经 BeaconAuth 网页登录进服，并保留 Mojang UUID（含未安装本模组的原版客户端）
# - 装有本模组的离线/社区账号仍可通过 BeaconAuth 网页登录进服
# 若为 false：所有人都必须走 BeaconAuth（未安装模组的原版客户端会被拒绝）
bypass_if_online_mode_verified = true
# 若为 true：服务器 offline-mode 时强制模组客户端认证
force_auth_if_offline_mode = true
# 仅在 force_auth_if_offline_mode 为 true 时生效
# 若为 true：offline-mode 时允许原版客户端（未装模组）进入
allow_vanilla_offline_clients = true
# 旧版离线身份模式（用于迁移已有的 offline-mode 服务器）：
# - 若为 true：每个 BeaconAuth 账户会被映射到其首次认证登录时声明的离线 UUID（"OfflinePlayer:<名字>"）
#   并从此固定使用该身份。
# - 世界数据（playerdata/、stats/、advancements/）无需改名即可保留。
# - 映射按世界存储于 <世界目录>/beaconauth-identities.json。
# - 安全提示：身份绑定首次登录时的用户名，之后以相同用户名注册的账户会映射到同一 UUID。适用于小型服务器。
use_legacy_offline_uuids = false
```

### 说明

- `authentication.base_url` 用于构建登录 URL 与 JWT issuer（`iss`）。
- `authentication.jwks_url` 为空时默认使用 `${base_url}/.well-known/jwks.json`。
- `jku.allowed_host_patterns` 为逗号/空格分隔的白名单。支持：
  - `example.com`、`*.example.com`
  - 不支持：裸 `*` 或 `auth*.example.com` 这类中间通配符
- 在 online-mode 且使用默认行为配置时：正版账号按原版多人游戏方式加入；离线账号需要安装 BeaconAuth 并完成网页登录。

### 迁移已有的 offline-mode 服务器（旧版离线身份）

1. 启用 `behavior.use_legacy_offline_uuids = true`，并保持服务器 offline-mode。
2. 每个玩家首次通过 BeaconAuth 登录时，模组会将该账户绑定到离线 UUID（`OfflinePlayer:<名字>`），
   并写入 `<世界目录>/beaconauth-identities.json`，现有 `playerdata/`、`stats/`、`advancements/`
   无需改名即可继续使用。
3. 若要规划迁移，请运行 `/beaconauth unmigrated`（权限等级 2）。它会列出 `playerdata/` 中
   尚未被任何 BeaconAuth 账户认领的每个离线档案（尽可能显示玩家名）；服务器启动时也会在
   日志中记录未迁移总数。
4. 旧版离线身份只能被认领一次：如果之后有其他 BeaconAuth 账户用相同游戏名登录，登录会被
   拒绝并给出明确提示，而不是静默绑定该身份。
5. 误操作补救：服务器管理员（权限等级 2）可用
   `/beaconauth transfer-identity <游戏名> <BeaconAuth用户名>` 转移身份。
6. 所有人迁移完成后映射仍会生效；之后再关闭该模式会让账户回到稳定的 per-account UUID
   （新世界数据，不再关联旧数据）。
